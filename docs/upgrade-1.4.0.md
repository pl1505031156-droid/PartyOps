# 党建智办 PartyOps 1.4.0 安装、升级与回滚

最后更新：2026-08-08

## 版本与数据迁移

- 程序版本：`1.4.0`；数据库模式：`0016`。
- 支持从 1.3.4/`0015` 前向迁移。升级保留事项、附件、重要档案、设备证书、共享目录、备份和 AI 配置。
- `0016` 为档案授权增加“贡献”能力，为共享目录增加审批说明，为评论保存提及用户，并为传输保存处理人、处理时间及业务关联。
- 既有 `selected` 档案授权继续保留查看/下载，贡献默认关闭；管理员须在“重要档案 → 类别授权”逐项补充贡献权限。

## 升级前检查

1. 在主机执行并验证最新 `.partyops-backup`，确认剩余空间可容纳数据库、附件和更新包的两份副本。
2. 记录当前主机/协同机角色；1.4.0 不再根据残留 `partyops.env` 猜测角色。旧配置无法判定时会进入恢复向导。
3. 正式环境只接受发布负责人签名且验证通过的 `partyops_1.4.0.partyops-update`。不得把未签名 Windows 候选安装器当作统一更新包导入。
4. 确认主机、协同 Agent 和更新助手可正常停止、启动，并保留上一版本同架构安装包。

## UOS 1.3.4 主机原位升级

1. 管理员进入“管理 → 系统更新”，导入已签名 `partyops_1.4.0.partyops-update`。
2. 更新器验证 Ed25519 签名、版本、架构、大小和 SHA-256，创建升级前备份。
3. 主机安装对应 `amd64` 或 `arm64` DEB，执行 `0015 → 0016`，再做健康检查。
4. 主机通过后，协同机获取匹配平台/架构制品并升级；旧更新器仍可读取 `architecture_artifacts` 中的 UOS 兼容映射。
5. 在“设备协同”确认共享根审批、目录授权、三种传输和收件箱处理均正常。

## Windows 10/11 x64 首次部署

1. 使用已做 Authenticode 签名且 SHA-256 与发布清单一致的 `PartyOps_1.4.0_windows_amd64.exe`。
2. 首次打开显式选择“主机”或“协同机”。主机数据位于 `%PROGRAMDATA%\PartyOps`；协同机配置和接收文件位于 `%LOCALAPPDATA%\PartyOps`。
3. 主机服务注册为 `PartyOpsHost`，更新服务注册为 `PartyOpsUpdateService`；防火墙只开放专用网络 TCP 18765、18766。
4. Windows 1.4.0 后续使用与 UOS 相同格式的签名 `.partyops-update`，由平台适配器选择 `platform_artifacts.windows.amd64`。

## 升级后重点验收

- 普通协同人员在获得贡献授权后，可从协同机新建、编辑并上传重要档案扫描件；无贡献授权时按钮和接口均拒绝。
- 档案校验错误显示到具体中文字段并聚焦首个错误；日期、数字、下拉和 `assessment_result` 按类别定义工作。
- 本机可重复管理共享文件夹；主机可批准/拒绝共享根并授权下载、分享、接收能力。
- 主机→设备、设备→主机、设备→设备传输均经主机审批/中转；收件箱可预览、下载、固化和关联。
- 评论追加不再争用事项版本；提及、回复、指派、审核、传输和共享目录审批通知可跳转。
- “我的工作”分别显示我主办、我协办、我审核和步骤分派给我。

## 回滚

- 安装器/程序失败：停止 PartyOps 服务，恢复上一版本同平台安装包；Windows 安装器卸载时移除服务、防火墙、协议和自启，但保留 `%PROGRAMDATA%\PartyOps` 与 `%LOCALAPPDATA%\PartyOps` 业务数据。
- 数据迁移失败：恢复升级前 `.partyops-backup`；不要把已写入 `0016` 的数据库直接交给 1.3.4 程序。
- 统一更新失败：平台适配器自动安装上一版本、恢复健康检查前状态并记录失败原因；仍失败时进入只读恢复页。

正式发布前仍必须在 UOS amd64、UOS arm64、Windows 10 x64 和 Windows 11 x64 分别完成主机/协同机实机矩阵。
