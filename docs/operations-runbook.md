# 党建智办长期运行与故障处置手册

最后更新：2026-07-29

## 1. 稳定运行原则

- 永远只有一台业务主机处于可写状态；灾备恢复前先停止旧主机。
- SQLite 数据库只放主机本地磁盘，不放共享盘、同步盘或 U 盘。
- 原始业务文件夹默认只读纳管；最终材料执行“固化归档”后才进入完整备份范围。
- AI 默认关闭、敏感事项禁止进入 AI；更新包必须通过内置 Ed25519 公钥验证。
- 不直接编辑数据库，不手工删除 `/var/lib/partyops`，不使用 `--force-architecture`。

## 2. 每日检查

管理员进入“系统设置 → 运行状态”，确认：

1. 主机状态正常，SSE 和后台任务没有持续失败；
2. 数据库、附件、原始索引和备份磁盘空间充足；
3. 最近一次自动备份成功；
4. 文件扫描、OCR、通知和报告队列没有长期卡住；
5. 没有异常隔离、证书过期或反复掉线的设备。

命令行只读检查：

```bash
systemctl is-active partyops
systemctl show partyops --property=ActiveState,SubState,NRestarts,Restart --no-pager
df -h /var/lib/partyops
sudo journalctl -u partyops -n 100 --no-pager
```

主机健康检查：

```bash
sudo curl --fail --silent --show-error \
  --cacert /var/lib/partyops/secrets/pki/ca.pem \
  https://127.0.0.1:18765/api/v1/health
```

结果必须包含 `status=ok`、`safe_version=true` 和 `fts5=true`。

## 3. 每周检查

- 手动执行一次备份，并把 `.partyops-backup` 与 `.sha256` 保存到第二台受控电脑。
- 检查终端灾备副本是否已拉取最新备份。
- 检查“未归档、材料缺项、逾期、等待反馈、待审核”智能文件夹。
- 检查离线设备、失败传输、更新失败和剩余中转配额。
- 下载一次诊断日志，确认没有持续重复的同一错误。

## 4. 每月与每季度检查

- 在隔离测试目录或备用电脑执行一次恢复演练，禁止直接覆盖正在工作的主机。
- 检查备份保留策略：14 个日备份、8 个周备份；手动备份不得被自动删除。
- 检查内部 CA、设备证书和磁盘寿命提示。
- 使用 `packaging/uos/target-acceptance.sh` 重新验证软件包、架构、OCR、桌面入口和连续健康检查。
- 季度更新前先在一台非主机终端验证安装包架构和桌面入口，再在维护窗口升级主机。

新装或升级后，建议先连续运行至少 1 小时；正式全面使用前运行 24 小时：

```bash
# 1 小时，每 10 秒检查一次
bash packaging/uos/soak-test.sh https://主机IP:18765 3600 10

# 24 小时，每 30 秒检查一次
bash packaging/uos/soak-test.sh https://主机IP:18765 86400 30
```

脚本记录健康检查失败、最大响应时间、systemd 重启次数和磁盘状态；只要出现健康失败或服务自动重启，结果即为失败。

## 5. 服务异常

先采集证据，不要反复重装：

```bash
systemctl status partyops --no-pager
sudo journalctl -u partyops -n 200 --no-pager
systemctl show partyops --property=NRestarts,ExecMainStatus,Result --no-pager
df -h /var/lib/partyops
```

若进程异常退出，systemd 会等待 5 秒自动拉起；5 分钟内最多尝试 10 次，避免无限快速重启。确认数据目录和磁盘正常后，可执行：

```bash
sudo systemctl restart partyops
```

仍失败时保持服务停止，保留日志和最近备份，再按“备份恢复手册”处理。

## 6. 主机不可用

1. 确认旧主机已经关机或停止 PartyOps；
2. 在灾备电脑安装相同架构或对应架构的 PartyOps；
3. 校验最新 `.partyops-backup` 和 `.sha256`；
4. 通过系统恢复入口恢复，不手工复制 SQLite 文件；
5. 配置新的固定局域网 IP，重新生成设备入网码；
6. 终端重新确认主机 CA 指纹后加入；
7. 执行目标机验收脚本，确认后才恢复日常写入。

旧主机修好后不能直接重新上线；必须先清除其写入资格或将其作为终端重新加入。

## 7. 更新发布顺序

1. 两种架构分别在 UOS V20 原生构建 `.deb`；
2. 执行测试、目标机验收和升级前恢复演练；
3. 在隔离发布机用离线私钥生成签名 `.partyops-update`；
4. 主机管理员导入更新包，先只升级主机；
5. 主机自动备份、迁移、健康检查全部成功后，再升级终端；
6. 离线终端上线后继续，失败设备单独重试；
7. 完成后手动备份并记录版本、数据库模式、包 SHA-256 和验收结果。

发布私钥不得复制到安装目录、单位终端、业务备份或发布 ZIP。当前打包脚本会扫描并拒绝包含发布私钥的 ZIP。

## 8. 长期版本冻结门槛

这次大版本进入单位正式使用后，原则上冻结业务功能，只做安全修复、数据修复和 UOS 兼容修复。冻结前必须全部满足：

1. 后端与前端发布测试门槛通过，含分支覆盖率不低于 90%，更新、恢复、权限、传输和任务状态机核心路径达到 100%；
2. UOS V20 amd64 与 ARM64 分别完成原生构建、双击安装、旧版本原位升级、桌面启动、重启持久化和卸载保留数据；
3. 使用真实结构的旧数据库执行一次升级和一次回滚，用户、事项、附件、模板、配对与备份数量核对一致；
4. 在隔离环境完成备份校验、恢复演练和主机故障后的灾备切换，确认不会同时存在两台可写主机；
5. 主机和至少一台 ARM64 终端连续运行 24 小时，健康检查失败为 0、服务自动重启为 0；
6. 多设备离线重连、权限撤销、文件中途变化、断点续传、磁盘不足和更新失败均完成故障回归；
7. 前端 1440×1024、1366×768 下主流程、居中弹窗、内部滚动和键盘操作通过浏览器验收；
8. 最终 `.deb`、便携包、`.partyops-update`、备份样本、SHA-256、数据库模式版本和验收记录归档。

冻结后采用“小步维护、集中升级”：

- 日常只做备份、证书、磁盘、设备和错误日志检查，不因界面偏好频繁升级；
- 非紧急功能建议先记录到需求清单，累计实际使用反馈后再统一规划下一版本；
- 涉及数据损坏、高危漏洞、UOS 系统升级不兼容或证书失效时，应立即走修复版本，不等待功能版本；
- 每次修复仍必须签名、备份、灰度一台终端、升级主机、再升级其余终端，不直接替换程序目录。

## 9. 禁止操作

- 禁止同时启动两个可写主机；
- 禁止强制安装错误架构包；
- 禁止把 18765 或 Agent 端口映射到公网；
- 禁止直接覆盖、删除或压缩正在使用的数据库；
- 禁止未经备份执行升级、恢复或灾备切换；
- 禁止把未签名更新包用于生产环境；
- 禁止为排查问题关闭权限、审计、哈希校验或路径校验。
